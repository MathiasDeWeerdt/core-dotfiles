**What explains the perceived quality.** My inference is that persistent asset identity, direct evidence links and visible uncertainty reduce the amount a model has to reconstruct from chat history. This is especially valuable on a retest or a handoff. A bound response still requires interpretation. For example, a recorded 403 can support a conclusion about the HTTP response, while the business operation's stored state remains unknown.

**Where the result can mislead.** The browser extension truncates long text and can omit binary bodies. Two matching hashes can therefore describe the same incomplete capture. The evidence guide also says automatic traffic binding is off by default and that reviewing traffic adds token cost. Record acquisition method, truncation and whether evidence was actually bound before treating a report as independently reviewable. [Extension implementation](https://raw.githubusercontent.com/BaaRai/ARTEX/486845c60db21e2a7ffa7eccbb9fa54d4758c6b5/extension/background.js) · [Evidence guide](https://raw.githubusercontent.com/BaaRai/ARTEX/486845c60db21e2a7ffa7eccbb9fa54d4758c6b5/docs/vulnerability-traffic-evidence.md)

**How to evaluate the claim.** Start with a fixed, sanitized evidence set with independently labeled defects, clean controls and inaccessible records. Give each reviewer the same inputs and time budget. Compare correct findings, false positives, missed labeled defects, duplicate rate, unsupported claims and time for a second reviewer to locate the source. Then replace one artifact and remove another. Check whether the earlier claims are marked stale or unavailable. Unit tests support claims about the report machinery. Detection quality needs this separate comparison.

## Keep a tooling lesson

If an engagement reveals a reusable tool behavior, reproduce it with a small synthetic input. Record the tool and version, input conditions, observed output, decision the agent should make, and when to revisit it. Add the lesson to the relevant reference. For a repeatable software defect, add a regression check. Keep client names, routes, artifacts and unreviewed conclusions in the engagement store.

One lesson from validating this skill was that a malformed dependency lockfile could yield an empty Syft inventory and a successful process exit. Trivy then processed the SBOM without identifying a language package. The [SBOM workflow](supply-chain.md) now checks the component list before interpreting a vulnerability count.
