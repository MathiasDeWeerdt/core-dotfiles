# Mathias — Global Agent Memory

Repository-specific instructions, established project conventions, and explicit task requirements take precedence.

## Context

* Preferred language: English
* Role: Developer and security specialist
* Primary environment: CachyOS / Arch Linux, Wayland, Zsh

## Core principles

* Make the smallest change that fully solves the task.
* Preserve existing behavior unless change is explicitly required.
* Do not perform unrelated refactors, formatting, renaming, or dependency upgrades.
* Follow existing repository architecture and conventions.
* Prefer simple, explicit code over clever abstractions.
* Reuse, repair, simplify, or delete before adding.
* Do not invent facts, APIs, files, command output, or test results.
* Distinguish verified facts, assumptions, and uncertainty.

## Workflow

Before editing:

* Read applicable repository instructions.
* Inspect relevant code, tests, configuration, and call sites.
* Search for existing utilities and similar patterns.
* Consider security and compatibility implications.

While editing:

* Keep changes focused and incremental.
* Preserve unrelated work.
* Do not expand scope without a concrete requirement.
* Do not weaken security, typing, validation, or tests.
* Remove temporary code, debug output, and scaffolding.

After editing:

* Read back changed code and inspect the diff.
* Run relevant formatting, static analysis, and tests.
* Inspect actual command output.
* Report what changed, what was verified, and what remains uncertain.

## Code quality

* Do not comment every function, variable, or obvious operation.
* Comments should explain intent, constraints, trade-offs, or surprising behavior.
* Prefer descriptive names, early returns, and focused functions.
* Avoid unnecessary wrappers, interfaces, helpers, and indirection.
* Do not create abstractions for hypothetical future requirements.
* Prefer minor obvious duplication over a misleading abstraction.

## Dependencies

* Search the repository before implementing functionality.
* Prefer existing project utilities and the standard library.
* Use mature libraries for complex, standardized, or security-sensitive functionality.
* Do not implement custom cryptography, authentication, protocol parsers, or serialization formats.
* Do not add dependencies for trivial functionality.
* Consider maintenance, license, security history, API stability, and transitive dependencies.

## Python

* Always use a project-local virtual environment for Python work.
* Prefer an existing environment such as `.venv`; otherwise create one with `python -m venv .venv`.
* Run Python and package commands through the environment, for example:

  * `.venv/bin/python`
  * `.venv/bin/pip`
* Do not install Python packages globally.
* Prefer the repository's existing tooling when present, such as `uv`, Poetry, Pipenv, or Hatch.
* Do not create a second environment when the project already defines one.

## Security and testing

* Treat external input as untrusted and validate it at trust boundaries.
* Use parameterized queries and structured APIs.
* Never log or commit secrets or credentials.
* Do not disable TLS validation, authentication, authorization, or other controls for convenience.
* Add or update tests when observable behavior changes.
* Reproduce bugs with a failing test when practical.
* Test behavior, relevant failures, and boundary conditions.
* Keep tests deterministic.
* Never claim tests passed unless they were run and their output was inspected.

## Tooling

For interactive work, prefer:

* `rg` over `grep`
* `fd` over `find`
* `eza` over `ls`
* `jq` for JSON

Use `cat`, `sed`, or repository-native tools for reading files. Do not use `bat`.

These preferences must not reduce script portability.

Do not:

* Run destructive commands without explicit authorization.
* Casually use `git reset --hard`, `git clean -fd`, recursive deletion, or destructive migrations.
* Install global packages when a project-local option exists.
* Manually edit generated files or lockfiles.
* Create commits unless requested.

## Communication and token efficiency

* Skip plans for simple tasks.
* Use a short checklist only for genuinely multi-step work.
* Do not narrate routine searches, file reads, edits, or successful commands.
* Avoid repeating the task, repository context, or previously established facts.
* Report only material changes, failures, risks, and validation results.
* Prefer concise summaries over full command logs.
* Include command output only when it explains a failure or proves an important result.
* Do not reproduce unchanged code or entire files unless requested.
* Show minimal diffs or relevant snippets rather than broad context.
* Do not restate repository instructions in responses.
* Ask questions only when ambiguity is costly, destructive, or security-sensitive.
* Report unrelated findings separately and do not fix them unless in scope.
* Default final responses to:

  1. Result
  2. Validation
  3. Remaining issue, only when applicable
* Do not provide a file-by-file summary when one sentence is sufficient.
* Do not explain standard syntax or routine implementation details.
* Do not include unchanged context around code snippets.
* Do not provide multiple alternatives unless requested or the choice is materially ambiguous.
* Do not add conclusions that repeat the preceding summary.
